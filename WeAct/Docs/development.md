# Устройство проекта

## Структура и ответственность

Структура следует примеру `SM`: C-модули с парными `.c/.h`, явными API, структурами состояния и отдельным прикладным слоем.

| Каталог | Назначение |
|---|---|
| `Core/Inc`, `Core/Src` | HAL-конфигурация и запуск, генерируемые CubeMX |
| `Core/Bsp` | Привязка кнопки, индикации и аппаратных драйверов к плате |
| `Core/Bsp/Camera` | SCCB, OV7725, заготовка OV5640, DCMI |
| `Core/Bsp/ST7735` | Драйвер экрана и SPI-порт |
| `Core/Bsp/Storage` | Реализация файлового API через FatFs и SDMMC |
| `Core/Bsp/USB` | Передача строк через USB Host CDC |
| `Core/Common` | Кнопка, календарные часы и общий ASCII-шрифт без зависимости от HAL |
| `Core/Camera` | Публичный API кадра и захвата |
| `Core/Media` | MP4/AVI, H.264/JPEG, преобразование пикселей и отметка времени |
| `Core/Storage` | Файловый API и библиотека `FatFs` |
| `Core/Recording` | Сеансы, фрагменты, виртуальный поток и объединение |
| `Core/UI` | Состояние меню, команды, представление и API дисплея |
| `Core/Timelapse` | Настройки, расписание съёмки и взаимодействие модулей |
| `Drivers` | CMSIS и STM32 HAL из пакета Cube |
| `MDK-ARM` | Сгенерированный проект µVision, startup и scatter-файл |
| `Tests` | Тесты переносимых модулей с моделью SD |

Прикладные настройки задаются в `timelapse_config.c`. Общие `button` и `avi` не зависят от приложения. Аппаратные компоненты не вызывают логику меню или записи. Файловая система обслуживается только основным циклом.

## CubeMX и Keil

`Timelapse.ioc` — источник конфигурации аппаратуры. Проект `MDK-ARM/Timelapse.uvprojx` создан STM32CubeMX 6.12.1 с STM32CubeH7 1.11.2, затем к нему подключены прикладные группы `Core/*`. В нём выбран Arm Compiler 6.19, MicroLIB и scatter-файл `Timelapse.sct`.

Вызовы `Board_Init`, `Timelapse_Init`, `Timelapse_Process` находятся в секциях `USER CODE` файла `main.c`; `Board_Tick` — в `SysTick_IRQn 1`. Сохраняйте `Keep User Code` при генерации. Не помещайте прикладную логику в генерируемые участки.

После повторной генерации CubeMX выполните из каталога `WeAct`:

```text
python Tools/configure_keil.py
```

Этот скрипт требует уже созданный CubeMX `.uvprojx`, добавляет исходники и include-пути, выбирает компилятор и scatter-файл. Он также применяет совместимость CDC ACM с протоколом 0 и ненулевым подклассом data-интерфейса в `usbh_cdc.c`; CubeMX может заменить этот файл штатным. Скрипт не генерирует HAL или отдельный проект. Для открытия и сборки готового проекта Python не нужен.

Инициализация SDMMC исключена из автоматических вызовов `main` в Advanced Settings CubeMX. Карту инициализирует `disk_initialize` при монтировании: сначала 1-битный режим, затем согласование 4-битного. Отсутствующая карта возвращает ошибку приложению, а не переводит запуск в `Error_Handler`.

## Аппаратура

Распиновка сверена с примерами WeAct `08-DCMI2LCD` и `04-SD_Test`.

| Сигнал | Вывод |
|---|---|
| K1, активный высокий уровень | PC13, подтяжка вниз |
| Светодиод | PE3 |
| SCCB SCL / SDA | PB8 / PB9, I2C1 |
| Камера XCLK | PA8, MCO1, HSI48 / 4 = 12 МГц |
| Камера PCLK / HREF / VSYNC | PA6 / PA4 / PB7 |
| Камера D0…D7 | PC6, PC7, PE0, PE1, PE4, PD3, PE5, PE6 |
| LCD CS / DC | PE11 / PE13 |
| LCD SCK / MOSI | PE12 / PE14, SPI4 |
| Подсветка LCD | PE10, TIM1_CH2N |
| SD D0…D3 / CLK / CMD | PC8…PC11 / PC12 / PD2, SDMMC1 |
| USB D− / D+ | PA11 / PA12, OTG_HS с внутренним FS PHY |

Частоты по конфигурации: HSE 25 МГц, SYSCLK 550 МГц, HCLK 275 МГц, APB 137,5 МГц, PLL1Q 55 МГц. SDMMC ClockDiv = 2 даёт рабочую SDCLK 13,75 МГц; начальная частота задаётся HAL при идентификации карты. SPI4 — 17,1875 Мбит/с.

OV7725 отдаёт RGB565, старший байт первым. Поддерживаются QQVGA и QVGA; кадровый буфер максимального размера занимает 153600 байт. VGA RGB565 требует 614400 байт, поэтому в меню не заявлен. Предпросмотр заполняет 160×80 с центральной обрезкой без изменения пропорций: из QQVGA показываются строки 20…99, из QVGA — область 320×160 начиная со строки 40 с уменьшением вдвое. Исходный кадр записи сохраняется полностью.

Экранный порт хранит копию предпросмотра размером 25600 байт. Прозрачные надписи с чёрной тенью накладываются до отправки соответствующих строк экрану; фон под изменившимся текстом восстанавливается из копии. Следующий DMA захват не меняет фон интерфейса.

`OV5640_Probe` читает ID через 16-битную адресацию SCCB. `OV5640_Init` явно возвращает отсутствие реализации; выбор неподдерживаемого сенсора не запускает захват.

## Захват и память

DCMI работает в snapshot-режиме с DMA1 Stream0, DMA_NORMAL и 32-битными передачами. Максимальная длина DMA — 38400 слов. Кадр выдаётся только после Frame callback и нулевого NDTR; тайм-аут незавершённого захвата — 1000 мс. Завершённый кадр принимается и после задержки основного цикла на SD. Перед каждым snapshot очищаются флаги DCMI и восстанавливаются IRQ ошибок, отключаемые HAL после кадра. Причина ошибки захвата сохраняется на экране. После записи регистров формата и окна OV7725 выдерживается 300 мс до первого захвата. COM3 сохраняет порядок выходных данных, зеркалирование и вертикальный flip выключены.

`Media/media_memory` занимает 320 КиБ AXI SRAM с адреса `0x24000000`. Первые 145024 байта отданы постоянному состоянию кодировщика, следующие 182656 — его рабочей памяти и захвату камеры. Приложение передаёт адрес драйверу через `Camera_SetBuffer`; драйвер не зависит от кодировщика. Сначала выполняются захват и предпросмотр, затем RGB565 преобразуется в YUV420 и H.264 использует прежний буфер RGB как рабочий. Следующий DMA начинается только после записи результата. До DMA выполняется очистка/инвалидация D-cache, после — инвалидация; адрес выровнен на 32 байта.

Яркость Y занимает 76800 байт DTCM, цветовые плоскости — 38400 байт ITCM, копия экрана и полоса вывода — 29440 байт SRAM D2. Стек 16384 байта, heap 8192 байта и остальные данные находятся в DTCM. `SystemInit` включает ITCM до инициализации C, `DATA_IN_D2_SRAM` включает тактирование SRAM D2. `configure_keil.py` восстанавливает эти настройки после CubeMX. JPEG использует тот же AXI-пул, а объединение и загрузка используют первые 16384 байта только при остановленной записи. USB-передача хранит собственную копию, поэтому незавершённая передача не ссылается на повторно используемый кадр. SDMMC и USB работают без DMA и могут использовать DTCM.

Кнопка опрашивается в SysTick; распознанные события передаются основному циклу. Одиночное нажатие выдаётся после истечения окна двойного. Долгое нажатие не порождает дополнительный click при отпускании. Переполнение 32-битного счётчика времени учитывается разностями без знака.

## Фрагменты и объединение

FatFs поддерживает FAT16/FAT32 и exFAT (`FF_FS_EXFAT=1`, `FF_USE_LFN=1`, `ffunicode.c`, code page 437). Статический LFN-буфер используется одним владельцем файловой системы. Имена, создаваемые приложением, остаются в формате 8.3. LBA — 32-битные секторы по 512 байт; 64 ГБ укладывается в адресацию. `Store_Stat64` и объединённый поток используют 64-битные размеры; смещения внутри исходного фрагмента остаются 32-битными. Перед объединением на карту проверяется предел файла FAT16/FAT32 или exFAT. Форматирование включено только в тестовой сборке; прошивка карту не форматирует.

Новая запись получает монотонный идентификатор каталога `0:/TL/Rnnnnnnn`. Фрагмент создаётся как `Fnnnnnnn.TMP` и синхронизируется каждые 25 кадров. При достижении заданного количества кадров или ручной остановке обновляется длительность в заголовке, файл синхронизируется, закрывается и переименовывается в `Fnnnnnnn.MP4`. Готовые фрагменты не открываются на запись. Ошибка завершает текущий сеанс. После перезапуска создаётся новый каталог; оставшиеся TMP не входят в объединение.

Приложение пишет H.264 Baseline/YUV420 в fragmented MP4 (`avc1`). `Media/h264_frame` преобразует RGB565 через две строки BGR, накладывает время и кодирует minih264; скорость `FASTEST`, диапазон QP 24–32, ориентир размера кадра `width * height / 24`, GOP равен частоте воспроизведения. Это параметры кодировщика, а не гарантированный битрейт или частота захвата. Каждый файл начинается с IDR; для 160×120 кодировщик сам описывает обрезку нижнего макроблока в SPS. `Media/mp4` хранит SPS/PPS в avcC, заменяет Annex B start codes длинами NAL, формирует init-заголовок 1024 байта и moof/mdat с накладными расходами 108 байт на кадр. При 25 кадрах/с варианты 30/60/120/300 секунд соответствуют 750/1500/3000/7500 кадрам. По умолчанию 300 секунд.

MJPEG/JPEGENC и DIB доступны файловому API для проверки совместимости AVI. JPEG использует качество `JPEGE_Q_HIGH`, выход 65536 байт и таблицу 7500 размеров в общем AXI-пуле; нехватка буфера возвращает ошибку.

`Recording/recording_stream` представляет фрагменты единым последовательным MP4 либо AVI без предварительной большой копии. Для MP4 проверяются формат и SPS/PPS, создаётся общий init-заголовок с длительностью всей сессии, а номера moof и временные метки tfdt сдвигаются по мере чтения; сжатые NAL копируются без перекодирования. Проверяются длины кадров и начало каждого файла с IDR. Пропуски нумерации и смешивание кодеков отклоняются. Для MJPEG каждый исходный фрагмент становится RIFF/AVIX: сжатые данные копируются, `idx1` преобразуется в `ix00` порциями, `indx` содержит 64-битные позиции. Для больших DIB-файлов `Media/avi_extended` формирует RIFF меньше 1 ГиБ. Тот же поток используется при объединении на карту и скачивании через ESP. `Store_Seek` пропускает обращение к FatFs, если позиция уже нужная.

Объединение пишет `ALL.TMP` порциями до 16384 байт. После успешного закрытия файл становится `ALL.MP4` или `ALL.AVI` по формату сессии. Отмена удаляет только временный результат; существующий объединённый файл не перезаписывается. Во время объединения съёмка остановлена. Экранный порт не отправляет повторно неизменившиеся строки меню, Wi-Fi и прогресса.

Разделение защищает уже закрытые фрагменты от ошибки, испортившей текущий файл. FAT не является журналируемой файловой системой: исчезновение питания во время изменения общей FAT или каталога всё ещё может повредить файловую систему. Испытания модели диска проверяют возврат ошибок I/O; это не имитация всех режимов потери питания SD-карты.

Раз в секунду приложение проверяет доступность карты через CMD13 или повторяет монтирование. При потере карты `Store_Reset` отзывает дескрипторы по поколению и деинициализирует SDMMC без попыток сбросить старые файлы на другой носитель. Запись/объединение прекращаются. Повторное подключение загружает настройки карты; запись возобновляется вручную новым сеансом.

Настройки хранятся в двух слотах с номером поколения и CRC32. При сохранении заменяется неактивный слот. При загрузке выбирается самая новая корректная копия. `TLC3` содержит индекс режима 24/10 кадров/с либо 1/5/10/30/60/120/300 секунд. Индексы `TLC1/TLC2` переводятся в новые значения; старые 600/1800 секунд ограничиваются 300 секундами. Для `TLC1` длительность фрагмента по умолчанию — 300 секунд.

Планировщик 24 кадров/с чередует периоды 41/42 мс с остатком, без накопления округления до 42 мс. При задержке до следующего кадра продвигает срок вперёд и пропускает просроченные интервалы, не создавая серию кадров задним числом. Период 10 кадров/с — 100 мс. Частота AVI остаётся 25 кадров/с. Реальную частоту съёмки определяют камера, вывод предпросмотра и SD; она не измерена модельными тестами.

## ESP32-S3, Wi-Fi и время

WeAct работает USB Host Full Speed, ESP32-S3 — Hardware CDC/JTAG. USB использует HSI48, SOF и polling основного цикла, без HCD DMA. В Cube настроены четыре интерфейса и три endpoint на интерфейс для составного дескриптора ESP. Heap — 8192 байта. Внешнее питание VBUS не коммутируется программно: обе платы питаются от общего источника. USB middleware взят из STM32CubeH7 v1.11.2, дерево `8c36b0df1228b63762c37673c754ab54f45180e9`. Проверка интерфейса сохраняет CDC class/ACM subclass, но допускает различия protocol и data subclass. DTR/RTS не переключаются.

Скетч `ESP32/TimelapseWifi` предназначен для Arduino IDE с esp32 3.3.2. Все файлы лежат рядом с `.ino`, по структуре `OpticalChannelTester`: короткие `setup/loop` вызывают `App::begin/update`, приложение связывает классы `CameraLink`, `WifiAccessPoint` и `Web`. Они отвечают за USB-протокол, управление AP и HTTP-интерфейс соответственно. `UsbSerial` отвечает за аппаратный транспорт: освобождает Arduino HWCDC и устанавливает штатный USB Serial/JTAG-драйвер ESP-IDF из пакета Arduino с RX 32768 и TX 2048 байт. Приём использует кольцевой буфер драйвера и локальный блок 1024 байта. Ожидание будится по поступлению данных, без обязательной задержки после каждого пакета. STM32 обслуживает CDC непрерывно до 1 мс за проход, с дополнительным ограничением числа итераций; команды и UI остаются в основном цикле. HTTP использует TCP_NODELAY. Параметры находятся в `Config.h`, HTML — в `WebPage.h` во Flash. Внешних веб-ресурсов и библиотек нет.

ESP раз в секунду отправляет `STATE <0|1>`, где число — фактическое состояние AP. STM32 отвечает `WIFI <0|1>` по текущему экрану UI. AP выключена при старте и после пяти секунд без ответа STM32; при ожидании файлового ответа тайм-аут составляет десять секунд. Экран STM32 показывает `WIFI: ON` только после свежего подтверждения включённого состояния ESP. Вход в режим закрывает текущую запись и останавливает камеру; двойное нажатие возвращает предпросмотр и запрашивает выключение AP. Карта для этого режима не требуется. После удаления пункта SESSION команда объединения использует последнюю сессию по номеру каталога.

HTTP `POST /api/time` принимает form-поля `utc` (целые секунды UTC, 2000–2099) и `offset` (минуты, −720…840). ESP передаёт строку `TIME <id> <utc> <offset>` и ждёт до пяти секунд `OK <id>`; `ERR <id>` или отсутствие подтверждения возвращают HTTP 503. Ложные подтверждения с другим номером игнорируются. USB обрабатывается и во время ожидания ответа на HTTP-запрос.

`Common/clock` ведёт программные часы по tick, с учётом переполнения и часового пояса. Они не сохраняются при сбросе STM32. Время фиксируется перед стартом каждого записываемого кадра. `Media/image_text` накладывает `ДД.ММ.ГГГГ ЧЧ:ММ:СС` белым шрифтом 6×12 с чёрной тенью при преобразовании строк в BGR24, до преобразования в YUV для H.264. Отступ снизу и слева — два пикселя. После преобразования H.264 использует память исходного кадра как scratch. До синхронизации отметка отсутствует.

HTTP `GET /api/recordings?after=N` и `/api/fragments?session=R&after=N` возвращают следующую запись/фрагмент или `null`; веб-страница отображает их порциями по 20. `/download?session=R&part=F` скачивает фрагмент, `part=0` — объединённый поток. Заголовок HTTP содержит 64-битный Content-Length и имя вложения; WebServer с 32-битным `size_t` для его формирования не используется. Чтение и запись сети выполняются блоками до 16384 байт. USB RX на ESP — 32768 байт, бинарная часть читается порциями; задержка используется только при отсутствии данных или прогресса. STM32 продвигает CDC bulk-состояния до 32 раз за вызов при активной передаче. Одновременно обслуживается одна загрузка. Обрыв соединения не дополняется фиктивными байтами: короткий ответ остаётся ошибкой скачивания.

`Tools/video_mp4.py` использует Python stdlib и внешний FFmpeg/libx264. HTTP-вход поступает в stdin FFmpeg, H.264 кодируется с CRF 18, preset fast, yuv420p и faststart. Длина загрузки сверяется с Content-Length; завершённый MP4 публикуется только после успешного завершения FFmpeg. Существующий файл не перезаписывается. Временный результат находится рядом с назначением и удаляется при ошибке. Путь к FFmpeg задаётся через PATH или `--ffmpeg`; зависимостей от локальных SDK и соседних рабочих каталогов нет.

`Recording/download` владеет чтением файлов и объединённого потока. Команды: `FILES id LIST after`, `PARTS session after`, `OPEN session fragment`, `READ token offset`, `CLOSE token` (все с префиксом `FILES id`). Ответ — `FILE id status token size length codec` и ровно `length` бинарных байт. `status` соответствует `Store_Result_t`; codec 0/1/2 означает DIB/MJPEG/H.264. ESP выбирает расширение и MIME по подтверждённому кодеку; список JSON содержит `format`. Текст внутри видео не интерпретируется как команды. Номер запроса защищает от старых ответов, token — от продолжения другого файла, offset должен совпадать с текущей позицией. Передача разрешена только в режиме Wi-Fi с доступной SD. Потеря карты, выход из режима или 10 секунд без чтения закрывают поток.

Вместе с STATE ESP передаёт `APSSID`, `APPASS` из Config.h и диагностическую строку `APINFO`; STM32 хранит их для UI. Во время ожидания бинарного ответа эти уведомления приостанавливаются. Диагностика устаревает через 3 секунды. Во время загрузки Web измеряет интервалы файлового запроса (SD, объединение и USB) и записи HTTP, считает байты на эти интервалы и передаёт строку `USB …K HTTP …K`. Значения в КиБ/с, это скорости отдельных последовательных участков, а не общая скорость скачивания; запись HTTP также включает работу сокетного буфера. Короткий интервал ограничен снизу 1 мс, индикация сверху — 99999 КиБ/с.

AP запускается после выключения радио и паузы 200 мс. Используются канал из Config.h, полоса HT20, адрес 192.168.4.1/24 и DHCP с начальным адресом 192.168.4.2. Предел мощности задаёт `WIFI_TX_POWER_QDBM=34` (настройка 8,5 dBm), затем проверяется чтением из драйвера. Это проверяемая настройка для диагностики нестабильного радио, а не измеренная мощность конкретной платы. Основание для проверки пониженной мощности — [первичные отчёты о похожем поведении SoftAP](https://github.com/espressif/arduino-esp32/issues/7232); они не доказывают причину на данной SuperMini. Через 300 мс после конфигурации проверяются событие старта AP, режим, SSID, видимость SSID, канал, IP, предел мощности и работа DHCP. Если за 2 секунды подтверждения нет, радио выключается и запуск повторяется через 2 секунды. В рабочем состоянии проверка выполняется каждую секунду; отсутствие клиентов не вызывает перезапуск. Проверка состояния драйвера не подтверждает фактическое излучение beacon и видимость сети на телефоне.

STM32 повторяет USB enumeration после 2 секунд без прогресса передачи или 8 секунд без входящих данных; зависшее перечисление подключённого устройства через 10 секунд перезапускает USB Host. Это восстановление транспорта, без сброса камеры или питания.

## Проверки

Сборка Keil использует `-O2`. Предпросмотр запускает следующий кадр без искусственной паузы; ST7735 получает каждый прямоугольник одним непрерывным блоком RGB565.

Для запуска тестов требуется GCC, Python 3 и Linux/WSL:

```text
python3 Tests/run.py
```

Тесты используют исходники приложения и настоящую FatFs; SD-карта заменена разреженными образами FAT16/FAT32 и exFAT размером 64 ГБ с MBR. Проверяются жесты K1 с дребезгом и переполнением tick, команды меню, резервная копия настроек, запись и выбор сеансов, объединение и отмена, чтение с произвольными границами порций, свободное место больше 4 ГБ и отказы записи. Отдельный Python-парсер проверяет RIFF, размеры, BGR-каналы, порядок строк и смещения индекса. Экранный тест исполняет настоящий `display_port.c` с моделью ST7735 и проверяет заполнение экрана в обоих разрешениях, порядок байтов RGB565, прозрачный текст и восстановление фона. Сборка тестов включает AddressSanitizer и UndefinedBehaviorSanitizer.

Проверка на плате: предпросмотр OV7725 в обоих разрешениях; все жесты K1; запись нескольких кадров с интервалами 5 и 30 секунд; воспроизведение объединённого MP4 на телефоне; остановка и повторный запуск; перезагрузка с сохранением настроек; отсутствие/заполнение карты; отключение питания во время записи и объединения с последующим чтением прежних фрагментов.

Тесты также проверяют все четыре границы длительности фрагментов, объединение многокадровых файлов, неполный последний фрагмент, вставку/извлечение карты и отзыв старых дескрипторов. Порт камеры и OV7725 исполняются с моделью SCCB/HAL: ориентация, RGB565 readback, пауза после настройки окна, повторный snapshot, поздняя обработка готового кадра, timeout и ошибки DMA/DCMI. Отдельный тест настоящего ST7735-драйвера проверяет окно 160×80 и передачу 25600 байт одним блоком. UI-тесты проверяют возврат к первому пункту меню и длительность всей сессии перед номером кадра. Эти проверки не заменяют испытания захвата и горячего подключения на плате.

Проверяются календарь, високосный день, часовой пояс, переполнение tick, команды синхронизации, состояние Wi-Fi и размещение отметки в настоящем записанном AVI без изменения исходного кадра. Для модели Arduino USB-протокола выполните `python3 ESP32/Tests/run.py` из корня репозитория (G++/Linux): включение/выключение AP, истечение связи, частичные строки, переполнение строки, ACK, неверный ACK и тайм-аут.

Сборка скетча через Arduino CLI использует тот же пакет, что Arduino IDE:

```text
arduino-cli compile --fqbn esp32:esp32:esp32s3:USBMode=hwcdc,CDCOnBoot=cdc,FlashSize=4M,PSRAM=disabled,PartitionScheme=default ESP32/TimelapseWifi
```

На устройстве отдельно проверяются USB-переподключение, включение AP из меню без SD, выключение при выходе/отсоединении USB, получение телефоном IP-адреса, установка времени из браузера и отметка в MP4 после возврата к съёмке.

Модель Wi-Fi проверяет параметры DHCP и мощности, ошибки этапов запуска, задержанное подтверждение, остановку работающей AP, потерю DHCP, скрытый SSID и повторное включение. Отдельно проверяется, что точка без клиентов не перезапускается. Модель USB проверяет непрерывное обслуживание передачи, зависание, сохранение передачи при наличии прогресса, отсутствие ответов и зависшую enumeration. Тест ESP исполняет `UsbSerial` с моделью штатного драйвера: ошибка установки, блоки разных размеров, двоичные данные и тайм-аут. Таймеры проверяются также через переполнение tick.

Тесты выгрузки сравнивают побайтно фрагмент и объединённый поток на настоящей FatFs, проверяют каталог, token, запрет передачи вне режима Wi-Fi, тайм-аут и извлечение карты. Модель ESP разбивает бинарный ответ на порции по 64 байта, включая строки команд внутри видеоданных, старые ответы и обрыв пакета. Тест OpenDML создаёт разреженный файл на 30000 кадров 320×240 размером больше 4 ГиБ; независимый Python-парсер проверяет все RIFF/AVIX, superindex и индексы кадров. Проверка сторонним декодером выполняется FFmpeg с переходом к 1199-й секунде и декодированием одного кадра.

Дополнительные проверки с FFmpeg (после основных host-тестов):

```text
python3 WeAct/Tests/verify_video.py --ffmpeg /path/to/ffmpeg
python3 WeAct/Tests/verify_mp4.py --ffmpeg /path/to/ffmpeg
python3 Tools/tests/test_video_mp4.py --ffmpeg /path/to/ffmpeg
```

Проверяются MJPEG и H.264/MP4 на FAT16/FAT32/exFAT, произвольные границы чтения, побайтовое совпадение объединения и потока, структура контейнеров независимым парсером, декодирование всех кадров FFmpeg, цвета и отметка времени. H.264 проверяется в обоих разрешениях с общим буфером камеры и scratch; объединённый MP4 содержит три независимых фрагмента с непрерывными временными метками. Отдельно утилита конвертации AVI в MP4 проверяется из файла и через локальный HTTP-сервер, включая обрыв загрузки и сохранность существующего файла. Скорость Wi-Fi, время сжатия на STM32 и частота съёмки требуют измерения на платах.

## Источники

- [minih264](https://github.com/lieff/minih264/tree/b0baea7a80ef9d12da97301dd1099b8791b5ba43), CC0. Заголовок и лицензия в `Media/MiniH264`. Локальное расширение `MINIH264_NO_SIMD` позволяет тестировать тот же скалярный путь на хосте; на Cortex-M7 используются доступные ARM DSP-инструкции. SVC, многопоточность и denoise отключены. Assert библиотеки отключён в MicroLIB-сборке; host-тесты используют assert и санитайзеры.

- [JPEGENC](https://github.com/bitbank2/JPEGENC/tree/f51421bdaba8e098dc82130a17adaae6d61c3377), Apache-2.0. В `Media/JpegEnc` сохранены лицензия и C-ядро. Локальные изменения заголовка: стандартные C includes вне Arduino; одинаковый 32-битный путь вывода кодов на STM32 и тестовом хосте, без невыровненных 64-битных записей. Обёртка резервирует 4096 байт перед границей выходного буфера.

- [WeAct MiniSTM32H723](https://github.com/WeActStudio/WeActStudio.MiniSTM32H723), ревизия `0a08d2808291a7ff38c8a4f89748693019257345`: распиновка, ST7735, ASCII-шрифт, таблица регистров OV7725.
- [STM32CubeH7 v1.11.2](https://github.com/STMicroelectronics/STM32CubeH7/tree/v1.11.2): HAL/CMSIS и код генерации. HAL submodule: `fec141ce999da655a48e1a15db83a72d564a1312`; CMSIS Device: `faccfec37f82f7a1319c21638111b0f7335de7fe`.
- [FatFs из репозитория ST](https://github.com/STMicroelectronics/stm32-mw-fatfs/tree/dd9126e957ae841a13ccbe2115d39a1fb7414126): `ff.c`, `ff.h`, `ffunicode.c`, `diskio.h`; конфигурация проекта находится рядом в `ffconf.h`.

Авторские уведомления сторонних исходников сохранены в файлах и соответствующих `LICENSE.txt`.
